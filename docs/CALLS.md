# Call System Architecture

**Last Updated**: 2026-03-27
**Status**: Implemented and working with Conversations.im and Dino

## Overview

Siproxylin implements audio/video calls using a hybrid Python + C++ architecture:
- **Python**: XMPP signaling (Jingle XEP-0166/0167/0353), SDP↔Jingle translation, GUI integration
- **C++**: Media handling via GStreamer webrtcbin (RTP, ICE, DTLS-SRTP)
- **Bridge**: gRPC communication between layers

**Why hybrid?**
- Python: Rich XMPP ecosystem (slixmpp), Qt GUI bindings
- C++/GStreamer: Battle-tested WebRTC stack (webrtcbin), better real-time media performance
- Separation: Signaling complexity isolated from media complexity

**Key Directories**:
- `drunk_xmpp/calls/` - XEP-0353 Jingle Message Initiation (Python, STABLE)
- `drunk_call_hook/` - gRPC client bridge (Python)
- `drunk_call_service/` - C++ media service (GStreamer webrtcbin)

**gRPC Interface**: `drunk_call_service/proto/call.proto`

## Encryption

### DTLS-SRTP (Always On)
- Standard WebRTC encryption for media streams
- Handled automatically by webrtcbin
- Fingerprint exchanged via SDP (`a=fingerprint:sha-256 ...`)
- Uses TLS certificates generated by GStreamer

**Key Point**: All calls are encrypted end-to-end via DTLS-SRTP. No plaintext media.

## GStreamer WebRTC Flow

### Pipeline Architecture

```
Outgoing Audio (Capture):
  pulsesrc → [webrtcdsp] → volume → queue → opusenc → rtpopuspay → webrtcbin → network

Incoming Audio (Playback, dynamic via pad-added):
  network → webrtcbin → rtpopusdepay → opusdec → queue → [webrtcechoprobe] → pulsesink
```

**Features**:
- Bundle: Single ICE connection for all media (`bundle-policy=max-bundle`)
- RTCP-MUX: RTP+RTCP on same port (automatic)
- Trickle ICE: Candidates streamed as discovered
- Opus codec: 48kHz, dynamic payload 97

### Outgoing Call Flow (Offer)

1. Create pipeline with webrtcbin element
2. Configure properties: bundle-policy, ice-transport-policy, STUN/TURN
3. Link audio source → encoder → webrtcbin
4. Set pipeline to PLAYING state
5. **Signal `on-negotiation-needed`** fires → emit `create-offer` action
6. **Promise callback**: offer ready → `set-local-description` → return SDP to Python via gRPC
7. **Signal `on-ice-candidate`** fires (multiple) → stream to Python via gRPC
8. Receive remote answer via gRPC → `set-remote-description`
9. **Signal `pad-added`** fires (incoming media) → create decoder chain dynamically
10. **ICE state**: NEW → CHECKING → CONNECTED
11. Media flows bidirectionally

### Incoming Call Flow (Answer)

1. Create pipeline with webrtcbin
2. Configure properties (same as outgoing)
3. Link audio source chain
4. Set pipeline to READY (not playing yet)
5. Receive remote offer via gRPC → `set-remote-description`
6. **CRITICAL**: Configure transceiver direction to SENDRECV **BEFORE** set-remote-description
7. **Promise callback**: offer set → `create-answer`
8. **Promise callback**: answer ready → `set-local-description` → return to Python
9. Set pipeline to PLAYING
10. ICE candidates exchanged, connection established

## SDP Negotiation

### Promise-Based Async API

GStreamer webrtcbin uses promises for asynchronous operations:

```cpp
// Create offer
GstPromise *promise = gst_promise_new_with_change_func(on_offer_created, session, nullptr);
g_signal_emit_by_name(webrtc, "create-offer", nullptr, promise);

// Callback fires when ready
void on_offer_created(GstPromise *promise, gpointer user_data) {
    const GstStructure *reply = gst_promise_get_reply(promise);
    GstWebRTCSessionDescription *offer;
    gst_structure_get(reply, "offer", GST_TYPE_WEBRTC_SESSION_DESCRIPTION, &offer, nullptr);

    // Set as local description
    g_signal_emit_by_name(webrtc, "set-local-description", offer, local_promise);

    // Convert to string and return via gRPC
    gchar *sdp_text = gst_sdp_message_as_text(offer->sdp);
}
```

### Critical Transceiver Direction Fix

**Problem**: Incoming calls showed "connected" on our side but "calling" on peer side (Dino).

**Root Cause**: webrtcbin creates transceivers with **RECVONLY** direction by default when processing incoming offers.

**Solution**: Set transceiver direction to SENDRECV **BEFORE** calling `set-remote-description`:

```cpp
// In create_answer() - webrtc_session.cpp:209-247
GArray* transceivers = nullptr;
g_signal_emit_by_name(webrtc_, "get-transceivers", &transceivers);

for (guint i = 0; i < transceivers->len; i++) {
    GstWebRTCRTPTransceiver* trans = g_array_index(transceivers, ...);
    g_object_set(trans, "direction",
                 GST_WEBRTC_RTP_TRANSCEIVER_DIRECTION_SENDRECV, NULL);
}

// THEN set remote description
set_remote_description(remote_offer);
```

**Why This Matters**: Transceiver direction property determines connection state, not just SDP attributes.

**Lesson Learned**: Don't add delays between set-remote-description and create-answer. Keep answer creation prompt (milliseconds, not hundreds of ms) to avoid timing-sensitive race conditions in GStreamer's WebRTC state machine.

## ICE Candidate Handling

### Local Candidate Generation

**Signal**: `on-ice-candidate` (fires multiple times after `set-local-description`)

**Candidate Types**:
- **host**: Local IP (192.168.x.x, 10.x.x.x)
- **srflx** (server reflexive): Public IP via STUN
- **relay**: TURN relay address

**Privacy Mode** (relay-only): Filter out host/srflx candidates to prevent IP leaks:

```cpp
void on_ice_candidate(GstElement *webrtc, guint mlineindex, gchar *candidate, ...) {
    if (session->relay_only) {
        if (strstr(candidate, "typ host") || strstr(candidate, "typ srflx")) {
            return;  // Skip non-relay candidates
        }
    }
    // Stream to Python via gRPC
}
```

### ICE State Machine

```
NEW → GATHERING → CHECKING → CONNECTED → COMPLETED
  ↓       ↓          ↓            ↓
FAILED  CLOSED  DISCONNECTED   FAILED
```

**Monitor via properties**:
- `ice-gathering-state`: NEW / GATHERING / COMPLETE
- `ice-connection-state`: NEW / CHECKING / CONNECTED / COMPLETED / FAILED

## Audio Processing (WebRTC DSP)

**Components**: `webrtcdsp` + `webrtcechoprobe` (gst-plugins-bad)

### Features
- Acoustic echo cancellation (AEC)
- Noise suppression (0=low, 1=moderate, 2=high, 3=very-high)
- Automatic gain control (AGC)
- High-pass filtering

### Architecture

Echo cancellation requires audio from **both directions**:

```
Capture:  pulsesrc → webrtcdsp → ... → webrtcbin
                      ↑ references probe
                      |
Playback: webrtcbin → ... → webrtcechoprobe → pulsesink
                             ↑ captures playback
```

**Critical Timing**: Create `webrtcechoprobe` during pipeline initialization as **unlinked element**, then link when incoming stream arrives (`pad-added` signal):

```cpp
// During pipeline creation (webrtc_session.cpp:814-827)
echoprobe_ = gst_element_factory_make("webrtcechoprobe", "webrtcechoprobe0");
gst_bin_add(GST_BIN(pipeline_), echoprobe_);  // Added but NOT linked

// Later, when incoming stream arrives
void on_incoming_stream(GstPad *pad) {
    // Link: depay → decoder → queue → echoprobe_ → audio_sink_
}
```

**Conditional Injection**: DSP elements only added when at least one feature is enabled (zero overhead when disabled).

**Configuration** (via protobuf):
- `echo_cancel`: boolean
- `echo_suppression_level`: 0-2
- `noise_suppression`: boolean
- `noise_suppression_level`: 0-3
- `gain_control`: boolean

## Threading Model

### GLib Main Loop Requirement

GStreamer signals fire in GLib main loop thread. Service runs dedicated main loop:

```
┌──────────────────────────┐
│  GLib Main Loop Thread   │  ← Start FIRST, runs g_main_loop_run()
│  - Processes signals     │
│  - Fires promise callbacks│
└──────────────────────────┘
           ↑
           │ Thread-safe signal emission
           │
┌──────────────────────────┐
│   gRPC Handler Thread    │  ← Can call GStreamer APIs
│  - CreateOffer()         │    (signals queued to main loop)
│  - Waits on condition    │
│  - Returns result        │
└──────────────────────────┘
```

**Key Rules**:
1. GLib main loop MUST be running for promises to complete
2. GStreamer callbacks execute in main loop thread
3. Use thread-safe queues/mutexes for gRPC ↔ GStreamer communication
4. gRPC handlers block on condition variables, signaled by promise callbacks

**Example**:

```cpp
// gRPC handler thread
Status CreateOffer(...) {
    // Trigger offer creation (queues signal to main loop)
    trigger_offer_creation();

    // Wait for result (signaled by promise callback in main loop)
    std::unique_lock<std::mutex> lock(session->sdp_mutex);
    session->offer_ready.wait(lock);

    return session->local_sdp;
}

// Main loop thread - promise callback
void on_offer_created(GstPromise *promise, ...) {
    // Extract SDP
    session->local_sdp = extract_sdp(promise);

    // Signal gRPC handler
    session->offer_ready.notify_one();
}
```

## Proxy Support

### HTTP Proxy
Set webrtcbin property:
```cpp
g_object_set(webrtc, "http-proxy", "http://proxy:8080", NULL);
```

### SOCKS5 Proxy
Configure via NiceAgent (ICE library):
```cpp
GObject *nice_agent;
g_object_get(webrtc, "ice-agent", &nice_agent, NULL);
g_object_set(nice_agent,
    "proxy-type", 2,  // SOCKS5
    "proxy-ip", "127.0.0.1",
    "proxy-port", 9050,
    NULL);
```

**Security Requirement**: MUST fail calls if proxy configured but unavailable (no fallback to direct connection).

## Statistics

**Method**: `get_stats()` (webrtc_session.cpp:297-373)

**Returns**:
- ICE connection/gathering states
- Bandwidth (calculated: delta bytes * 8 / time_ms)
- Packet loss, RTT, jitter (from RTP stats)
- Connection type (P2P direct/srflx, TURN relay)
- Active candidates when connected

**Implementation**: Use `get-stats` action with promise, parse GstStructure reply.

## Security Considerations

1. **Proxy Isolation**: Per-account proxies prevent traffic correlation
2. **Relay-Only Mode**: Forces TURN, prevents IP leaks
3. **Leak Prevention**: Fail calls if proxy unavailable (no direct fallback)
4. **DTLS-SRTP**: All media encrypted end-to-end

See: `docs/ADR.md` security requirements section.

## Known Issues & Workarounds

### Issue: on-negotiation-needed fires multiple times
**Cause**: Normal if transceivers change
**Workaround**: Track negotiation state, ignore if already negotiating

### Issue: No audio output
**Symptom**: Connection succeeds but no sound
**Debug**: Check `GST_DEBUG=pulsesink:5` for device errors, verify transceiver direction is SENDRECV

### Issue: ICE stuck in GATHERING
**Symptom**: Candidates never complete
**Cause**: STUN/TURN timeout (firewall or server unreachable)
**Debug**: `GST_DEBUG=nice:5` to see ICE activity

### Issue: DTLS handshake failure
**Symptom**: Connected but no media flows
**Cause**: Fingerprint mismatch or certificate issue
**Debug**: Check SDP `a=fingerprint` attributes match on both sides
